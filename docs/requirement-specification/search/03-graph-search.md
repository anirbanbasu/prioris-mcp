# Graph search

**v3** — see [SRS overview → Scope](../index.md#v3). `index.md`'s scope already named a `GraphBackend` — "cross-paper concept linking," automatic discovery of relationships between documents/notes — as future work, undesigned, alongside `VectorSearchBackend`. This chapter is where that gets designed: a `GraphSearchBackend` interface, its storage/query engine, and how it gets populated — kept deliberately separate from [Vector search](02-vector-search.md) and [Discovery](../02-discovery.md) so the topics don't drift into one undifferentiated discussion.

## Concrete engine: graphqlite, a Cypher-to-SQL transpiler over the same SQLite file

`graphqlite` (`colliery-io`) is `GraphSearchBackend`'s concrete engine, chosen over KuzuDB-derived forks (LadybugDB, Vela), `agentflare-ai/sqlite-graph`, and a plain-SQLite recursive-CTE fallback — see [ADR-00027](../ADR/00027-graph-engine-graphqlite.md) for the full diligence and comparison.

MIT-licensed, actively maintained, 97.7% openCypher TCK conformance, built-in graph algorithms (PageRank, Louvain, Dijkstra) — real Cypher, not a hand-rolled subset. Architecturally it's a transpiler, not a custom storage engine: Cypher is parsed to an AST and compiled to SQL against its own EAV schema, executed through SQLite's standard APIs. Its Python binding supports `wrap()` on an already-open stdlib `sqlite3.Connection`, so it extends the same connection pattern `StorageBackend`, `SqliteFts5SearchIndex`, and `sqlite-vec` already use — not a second persistence engine parallel to SQLite, the exact shape [Vector search](02-vector-search.md#engine-sqlite-vec-asg017) rejected ChromaDB/LanceDB for.

This also resolves the apparent tension between wanting a real graph query language and wanting the engine to stay swappable: `GraphSearchBackend`'s read/traversal surface stays defined in graph-operation terms (`get_nodes`/`get_edges`/`neighbors`, see "Read/traversal interface," below) rather than as raw Cypher passthrough, exactly mirroring the write side's already-engine-agnostic `add_node`/`add_edge`. `graphqlite` is today's implementation of that contract; a future hosted graph database becomes a straightforward second implementation of the same contract later, not an interface change.

This also closes [Vector search](02-vector-search.md#interfaces-stay-separate-even-if-a-future-engine-could-serve-more-than-one)'s "share an engine across FTS/vector/graph" question by elimination rather than by further diligence: `graphqlite` is Cypher-only, with no FTS/vector capability to share.

**A real correctness bug was found and worked around, not papered over — see [ADR-00027](../ADR/00027-graph-engine-graphqlite.md) for the discovery.** Creating a relationship between two nodes bound by a preceding `MATCH` (the dominant real-world case — connecting two already-existing nodes) and then `RETURN`ing the relationship variable, or a property on it, raises `Error('Unknown variable: r')` — but the underlying `CREATE` commits anyway. Filed upstream as [colliery-io/graphqlite#95](https://github.com/colliery-io/graphqlite/issues/95). Until fixed, `GraphSearchBackend`'s implementation must treat this as a hard constraint: never `RETURN` the relationship variable or its properties in the same call as a `CREATE` linking pre-existing nodes — issue the `CREATE` bare, then a separate follow-up read if the caller needs the new edge's id/properties back. Equally load-bearing: a raised exception from this specific pattern must not be treated as "the write didn't happen" for retry-on-error logic, unless the workaround above is applied unconditionally to sidestep the ambiguity entirely.

## Graph algorithms: implemented independently via NetworkX, not delegated to the engine

Whole-graph algorithms (PageRank, Louvain community detection, Dijkstra shortest path) raised a correctness question the read/traversal primitives don't have: every one of them must run over the **override-resolved** graph — a `reject`ed edge still shaping another node's PageRank score, or a cascade-pruned node still counted in a community, would silently defeat the human veto the override layer exists to provide. That requirement turned out to be far more expensive to satisfy than it first looked.

The settled override storage model (an `add`/`reject` record patch layer, not overrides mutated into base rows — see [ADR-00029](../ADR/00029-human-overrides-patch-layer.md)) resolves cleanly via a live SQL view over base + override tables for `get_nodes`/`get_edges`/`neighbors`. It does not, however, work for engine-native algorithm calls — see [ADR-00028](../ADR/00028-graph-algorithms-networkx-not-engine.md) for why, and for the alternative considered and rejected.

**Settled: algorithms are implemented independently of the engine, behind a `GraphAlgorithmsBackend` interface, using [NetworkX](https://networkx.org/) as today's implementation.** `GraphAlgorithmsBackend` exposes named algorithm methods (the catalogue settled below) as a thin wrapper, not a passthrough to any specific library — the same swap-point pattern this document already uses for `EmbeddingBackend` and for `GraphSearchBackend`'s own engine. Its NetworkX-backed implementation pulls the override-resolved node/edge set — via the same live-resolution mechanism `get_nodes`/`get_edges`/`neighbors` already need, not a separate materialized copy — builds an in-memory `networkx.Graph`/`DiGraph`, and runs NetworkX's own vetted implementation. This keeps resolution singular (one live query-time step, feeding both targeted reads and algorithm bulk-export) rather than the two-mechanism hybrid a materialized-table workaround would have required, and it restores engine independence twice over: `GraphSearchBackend`'s engine only ever needs to answer "give me the nodes/edges," and `GraphAlgorithmsBackend`'s own implementation can be swapped later — a faster library, or a native-code-backed system — without callers changing, since they only ever see `GraphAlgorithmsBackend`'s method signatures, never NetworkX's.

Kept on file as future `GraphAlgorithmsBackend` swap candidates, not adopted now: [`python-igraph`](https://igraph.org/python/) and [`rustworkx`](https://www.rustworkx.org/) are the most credible options if NetworkX's pure-Python cost ever becomes a real bottleneck — both C/Rust-core, both a plain `pip install` with no exotic build dependency, both with broad algorithm-catalogue overlap with NetworkX. [`graph-tool`](https://graph-tool.skewed.de/) benchmarks faster still but has no real PyPI wheel (conda/Homebrew only), a real cost against it. [`NetworKit`](https://networkit.github.io/) targets genuinely huge, multi-core-parallel workloads, and is the more plausible answer if `GraphSearchBackend`'s own engine is ever swapped for a remote, billion-edge, multi-user store — a scenario this document's engine-independence design already anticipates, not a new concern. GNN frameworks (DGL, PyTorch Geometric) and GPU-dependent options (RAPIDS cuGraph) were considered and dropped as the wrong problem shape entirely — neural-network-training infrastructure and a hard GPU dependency respectively, not classical graph algorithms.

**Algorithm catalogue, selected for this project's actual research use cases** — not mirrored from whatever `graphqlite` happened to expose natively:

- `pagerank` — the most "central"/important concepts or documents in a retrieved subgraph.
- `louvain` — cluster a subgraph into topic groups, a literature-review-style grouping of a research area.
- `dijkstra` (point-to-point and single-source) — explain how two specific concepts/documents are connected, relation-chain reasoning between two lookup results.
- `betweenness_centrality` (k-sampled approximate only — see "Expensive-tier algorithms," below) — surface "bridge" nodes spanning multiple topic clusters, boundary-spanning/interdisciplinary work.
- `weakly_connected_components` — a corpus-coverage check: is a node actually connected to the rest of the graph, or an orphan.
- `ancestors`/`descendants`/`topological_sort` — for DAG-shaped relation types (`cites`, `extends`, `refutes`, or similar dependency-like relations), the mathematically rigorous way to trace an idea's provenance: what a concept/document builds on, transitively, and what builds on it. `topological_sort` raising `NetworkXUnfeasible` on a cyclic subgraph is a feature, not a failure mode to hide — a citation loop is a real data-quality signal worth surfacing, not silently swallowing.
- `k_core` — distill a noisy domain down to its densely-debated core, filtering out one-off publications from what's actively engaged with by the field.
- `maximal_independent_set` — surface a maximally diverse, mutually non-adjacent set of papers/concepts, for presenting orthogonal viewpoints or opposing camps rather than a top-N list that's mostly one clique agreeing with itself. NetworkX's implementation finds *a* maximal set (locally can't add more), not the *maximum* one (NP-hard) — an accepted approximation, not a shortfall, since exact maximum independent set is intractable at any real scale regardless of implementation.
- `clustering`/`transitivity` — per-node/global clustering coefficient; low clustering around a node whose neighbors don't interact with each other signals a synthesis paper bridging otherwise-unconnected schools of thought. Subsumes standalone triangle count (same underlying computation, clearer research value) — triangle count alone was dropped from the catalogue.
- `minimum_spanning_tree` — extract a cluster's backbone (e.g. a `louvain`-identified topic group) as a linear, non-redundant reading sequence covering the cluster's intellectual breadth with the fewest conceptual leaps.
- `preferential_attachment` (link prediction) — see "Link prediction," below, for why this replaced the originally-proposed Jaccard/Adamic-Adar.

**Link prediction: `preferential_attachment`, candidate-set-bounded, not scored over every non-adjacent pair.** Chosen over Jaccard coefficient, Adamic-Adar index, and `resource_allocation_index` — see [ADR-00030](../ADR/00030-link-prediction-preferential-attachment.md) for the benchmarks and the framing tradeoff (degree-based popularity vs. shared-neighborhood "structural holes").

Scoring every non-adjacent node pair isn't viable at any real scale — at 50,000 nodes that's ~1.25 billion pairs — so `preferential_attachment` is always invoked over an explicit, bounded candidate-pair set (e.g. a query node's 2-hop non-adjacent neighborhood) supplied by the caller, never "the whole graph." Validated that cost tracks candidate-set size, not corpus size: sub-2ms for a single query node's ~400-pair neighborhood, 13.85ms for 50 query nodes' combined ~18,864-pair neighborhood, both at 50,000-node/500,000-edge scale — meaning this stays cheap regardless of how large the underlying corpus grows, as long as the candidate set stays bounded.

**Performance was validated at three scales, not assumed — including a scale intentionally pushed to a realistic upper bound**, not just a toy graph. 1,000 nodes/5,000 edges (two rounds — `pagerank`/`dijkstra`/`louvain`/`weakly_connected_components`/`triangles` first, then `k_core`/`maximal_independent_set`/`clustering`/`transitivity`/`minimum_spanning_tree`/`ancestors`/`descendants`/`topological_sort`/link prediction second) kept every algorithm in this catalogue under 15ms once numpy/scipy's one-time import cost (paid once at process startup, not per call) is excluded, with two exceptions: exact betweenness centrality (O(V·E), 2.34s at this scale — not adopted; see "Expensive-tier algorithms," below) and link prediction scored over literally every non-adjacent pair (629ms–1.26s — not how it's actually invoked, per "Link prediction," above).

50,000 nodes/500,000 edges was then tested deliberately — sized to represent a plausible upper bound for a single researcher's reading list (50,000 papers, more once each paper's notes/chunks/concepts are counted as their own nodes), not an arbitrary stress number. Every algorithm in the settled catalogue stayed under 1.3 seconds at this scale *except* `louvain` (13.7–14.8s) and approximate `betweenness_centrality` (k=100: 58.1s) — both addressed immediately below. Link prediction, tested bounded rather than exhaustive at this scale (per "Link prediction," above), stayed under 90ms for a 50-query-node candidate batch.

### Expensive-tier algorithms: `louvain` and approximate `betweenness_centrality`, run as long-running calls with progress reporting, not ordinary synchronous tool calls

At 50,000-node/500,000-edge scale, both cross into the range where a caller waiting on an ordinary synchronous MCP tool response would plausibly give up before it returns. Both use FastMCP's existing `Context` — already a parameter (`ctx: Context`) on every tool method in this codebase, currently unused in tool bodies — calling `ctx.report_progress(progress, total, message)` (a real, already-available FastMCP API, confirmed via `inspect.signature`) periodically while the algorithm runs, so the caller sees the call is alive rather than just hanging. This is a single, longer-running tool call, not a submit-now/poll-later job pattern — no new job-tracking state or session mechanism is needed, unlike e.g. the existing chunked-upload begin/finalize flow for local files.

`betweenness_centrality` gets a `k` parameter (default `25`, hard-capped at `100`) controlling the number of sampled source nodes the underlying k-sampled Brandes' algorithm uses — validated, not assumed: k=25 measured at 14.0s, k=100 at 58.1s (roughly linear in k, as expected for an O(k·E) algorithm), both at 50,000/500,000 scale. NetworkX's `backend="parallel"` dispatch ([`nx-parallel`](https://github.com/networkx/nx-parallel), a joblib-based official NetworkX backend) is adopted for this specific call, confirmed to genuinely help here — k=25: 4.67s, a 3.0x speedup; k=100: 10.1s, a 5.8x speedup, on a 10-core test machine — bringing even the k=100 ceiling close to what k=25 cost without it. The parallel backend caches a converted copy of the graph on the source `networkx.Graph` object and warns if that graph is later mutated in place without invalidating the cache; not a concern here, since `GraphAlgorithmsBackend` always builds a fresh graph object per call from a live override-resolved export, never a long-lived mutated one.

`louvain` has no equivalent tunable, despite looking for one: NetworkX's `max_level` parameter (capping the number of hierarchical aggregation passes) was tested at 50,000/500,000 scale and found to behave as a cliff, not a dial — `max_level=1` gave a real speedup (5.48s, at the cost of much coarser communities) but `max_level=3` (15.0s) was barely different from uncapped (14.8s), meaning most of the cost is incurred within the first few passes regardless of where the cap sits. Not adopted as a user-facing parameter for that reason. NetworkX's `backend="parallel"` also doesn't cover `louvain_communities` at all — confirmed via its registered function list, which has no community-detection entry. `louvain` therefore stays on its default settings, on the same async/progress-reporting tier as `betweenness_centrality`, simply because it's inherently this expensive at this scale — not because a tunable is being deliberately left off, and not because it's been ruled out: of everything tested for community detection, it remains the best choice, see below.

**Faster community-detection alternatives to `louvain` were tested and rejected, on quality grounds, not just kept for speed** — `greedy_modularity_communities` and label propagation; see [ADR-00031](../ADR/00031-community-detection-louvain.md) for the benchmarks. `louvain` remains the settled choice for community detection — kept, not ruled out, purely relocated to the expensive/async tier established above.

## Algorithm signatures: shared `node_ids` scoping, bounded parameters, and configurability

These are `GraphAlgorithmsBackend`'s own Python method signatures, one per algorithm, matching the MCP tool names 1:1 (see "MCP tool wiring," below — `research_graph_<algorithm_name>`). Every one of them takes a shared `node_ids: list[str] | None = None` parameter: the catalogue's own research-value framing repeatedly names "a *retrieved* subgraph" (`pagerank`: "in a retrieved subgraph"), not "the whole graph," so scoping has to be a real, first-class parameter rather than an afterthought. `None` means run over the whole override-resolved graph.

```python
pagerank(node_ids: list[str] | None = None, alpha: float = Field(0.85, gt=0, lt=1)) -> dict[str, float]
louvain(node_ids: list[str] | None = None, resolution: float = 1.0, seed: int | None = None) -> list[list[str]]
betweenness_centrality(node_ids: list[str] | None = None, k: int = Field(25, ge=1, le=100)) -> dict[str, float]
weakly_connected_components(node_ids: list[str] | None = None) -> list[list[str]]
ancestors(node_id: str, node_ids: list[str] | None = None) -> list[str]
descendants(node_id: str, node_ids: list[str] | None = None) -> list[str]
topological_sort(node_ids: list[str] | None = None) -> list[str]
k_core(node_ids: list[str] | None = None, k: int | None = None) -> list[str]
maximal_independent_set(node_ids: list[str] | None = None, seed: int | None = None) -> list[str]
clustering(node_ids: list[str] | None = None) -> dict[str, float]
transitivity(node_ids: list[str] | None = None) -> float
minimum_spanning_tree(node_ids: list[str] | None = None) -> {"nodes": [str, ...], "edges": [{"source_id", "target_id", "edge_id"}, ...]}
preferential_attachment(candidate_pairs: list[tuple[str, str]]) -> list[{"source_id", "target_id", "score": float}]
dijkstra(source_id: str, target_id: str | None = None, node_ids: list[str] | None = None)
    -> {"target_id": str | None, "distance": float | None, "path": list[str] | None, "distances": dict[str, float] | None}
```

`clustering`/`transitivity` stay two separate calls, despite both descending from the same settled catalogue entry: FastMCP derives one static output schema per tool, and a per-node `dict[str, float]` versus a single global `float` aren't reconcilable into one schema the way `dijkstra`'s always-both-fields-present-but-sometimes-null shape below is.

`dijkstra`'s return unifies its two modes the same way `research_arxiv_parse_full_text`'s `total_pages`/`page_range` are always present but `null` for a non-page-aware call ([06](../06-interface-specification.md#conventions)): point-to-point (`target_id` given) populates `distance`/`path`, leaves `distances` null; single-source (`target_id` omitted) populates `distances`, leaves `distance`/`path`/`target_id` null. `source_id` not resolving to an existing node fails `not_found`.

`weight` (added to the edge shape below) is what `dijkstra`, `minimum_spanning_tree`, and `pagerank`'s implicit edge weighting read from — there's no separate `weight_property` parameter naming where to look, since it's now a fixed field rather than an open metadata key.

`k_core`'s `k: int | None = None` means "use the maximum core number" (auto-distill to the densest core) rather than requiring the caller to already know a graph's own core structure — matching the tested pattern (`core_number` then `k_core(k=max_k)`) and the catalogue's own "distilling the debate" framing.

`topological_sort` on a cyclic subgraph raises a new typed exception, `GraphCycleError` (category `cyclic_subgraph`), not `invalid_request`: the caller's request was valid, the *data* is cyclic, and folding this into a category that implies caller error would undercut the catalogue's own framing of a citation loop as "a real data-quality signal worth surfacing, not silently swallowing." Every other failure mode across this catalogue reuses the existing `not_found`/`invalid_request` categories from [06](../06-interface-specification.md#conventions) — `GraphCycleError` is the one genuinely new addition.

**Bounding is via `Field` constraints on the parameter itself** (`k: int = Field(25, ge=1, le=100)`, `alpha: float = Field(0.85, gt=0, lt=1)`), not a manual check inside the method body — the same mechanism `research_arxiv_search`'s `max_results` bound already uses ([06](../06-interface-specification.md)): FastMCP derives the tool's JSON schema straight from the annotation, so the bound is visible to a calling client before it ever calls the tool, and a violation fails `invalid_request` automatically via Pydantic validation rather than a hand-written guard.

**Hard caps, not defaults, are `EnvVars`-configurable.** `betweenness_centrality`'s `k<=100` cap is exposed as an environment variable — the same reasoning `PRIORIS_MCP_LOCAL_FILE_MAX_SIZE_BYTES` already established: the cap was derived empirically against this project's own test hardware and graph sizes, and a different deployment might legitimately need a different ceiling, an operator/deployment concern rather than a per-call one. The `k=25` default stays a fixed code constant — it's already caller-overridable per request up to whatever cap is configured, so an env var would be a redundant second knob for something a caller can already adjust directly.

**MCP tool wiring: one tool per algorithm, not a dispatcher.** Fourteen separate tools, `research_graph_<algorithm_name>` (`research_graph_pagerank`, `research_graph_louvain`, `research_graph_dijkstra`, ...; no extra "algo" infix, matching `research_graph_status`'s own naming), same `ResearchPublicationProvider`-scoped prefix reasoning as "Write primitives," above — chosen over a single dispatcher tool; see [ADR-00032](../ADR/00032-algorithm-tools-one-per-algorithm.md) for why. `louvain`/`betweenness_centrality` need nothing structurally different at the registration level for being on the async/progress tier — that's a behavioural distinction inside the tool body (calling `ctx.report_progress`), not a different tool shape.

## Provider-grouping isolation: constructor-level seam already exists, config/registry still deferred

Every tool name settled in this document (`research_graph_*`) and every backend design (`GraphSearchBackend` as a single, corpus-wide instance) implicitly assumes one provider grouping — `ResearchPublicationProvider`, the only one that exists. See [Architecture → Provider groupings](../01-architecture.md#provider-groupings): the constructor-level seam (`grouping_dir`) that isolates a grouping's storage now exists and applies uniformly to `StorageBackend`/`SearchIndex`/`NotesBackend`/`NotesSearchIndex`; once `GraphSearchBackend` is implemented, it takes its storage location through that same seam rather than needing a bespoke isolation mechanism of its own. What's still deliberately undesigned, here as in Architecture, is the config/registry that would decide which groupings are active and route a call to the right constructed instance — deferred alongside `PatentProvider` itself, which remains out of scope for v1.

## Three input layers write through one interface, not three backend implementations

`GraphSearchBackend` exposes low-level `add_node`/`add_edge` write primitives, tagged with a required provenance field on every write. The three input layers named in this document's original scope are three different *callers* of that same interface, not three separate backend implementations:

- **Structural layer** — pure code (the parse pipeline, or a method on `GraphSearchBackend` itself), deterministically deriving nodes/edges from chunk/heading/document/note hierarchy. Calls the write primitives directly. Not pluggable — there's no swappable "structural extraction backend." Citation-graph data (in-document reference lists, or externally-sourced via OpenAlex/CORE per [Discovery](../02-discovery.md)) was considered for this layer and excluded — see "Citation-graph data excluded from the structural layer, for now," below.
- **LLM-extraction layer** — mirrors `EmbeddingBackend` exactly: a `GraphExtractionBackend` interface (`extract(text) -> (nodes, edges)`), injected into a `GraphSearchBackend.index_entries(text, ...)` convenience method the same way `EmbeddingBackend.embed(text)` is injected into `VectorSearchBackend.index_entries`.
- **Human layer** — direct CRUD via new MCP tool(s) built on the generic `add_node`/`add_edge` primitives plus the human-only `reject`/`edit_node`/`edit_edge`/`edit_reject` primitives (see "Write primitives," below), extending `index.md`'s already-named-but-undesigned "manual cross-document note relations" item. See "Human overrides," below, for why this isn't simple CRUD on the same rows the other two layers write.

### Provenance: a flat type plus an open metadata dict, with a minimum required subset per type

Every node/edge carries `{"type": "structural" | "llm_extracted" | "human_annotated", "metadata": {...}}`. `metadata` is an open dict — its exact contents are caller-supplied and not exhaustively specified here — but each type has a minimum required subset the interface validates:

- **`structural`** requires `source` — currently always `"internal_parse"` (this project's own parse pipeline); externally-sourced values such as `"openalex"`/`"core"` were considered and are deferred, not in use — see "Citation-graph data excluded from the structural layer, for now," below. The field stays open-valued rather than a closed enum, so a future source doesn't need a schema change to add.
- **`llm_extracted`** requires `model` and `extraction_mode` (`"single_pass"` | `"multi_pass_agentic"`); `version` and other run configuration are optional metadata rather than folded into the type string itself.
- **`human_annotated`** requires `annotator` (an opaque identifier), plus operation-specific fields — see "Human overrides," below.

**Naming.** `"structural"` was briefly reconsidered as `"deterministic"` (to better cover externally-sourced data like OpenAlex/CORE alongside in-document structure) and reverted: "deterministic" implies a permanence this data doesn't actually have (see cascade eligibility, below), which would read as contradictory. `"structural"` stays. `"human"` became `"human_annotated"` — it needs to cover both fresh human authorship and human review/correction of existing entries (see "Human overrides"), and "annotated" reads more naturally across both than "human" alone does.

## Cascade eligibility: `structural` and `llm_extracted` are regenerable, `human_annotated` additions are not

When a document is deleted (`research_delete_fetched`), its `structural` and `llm_extracted` nodes/edges are cascade-eligible for removal — both are machine-derived and regenerable, with no independent human investment. This holds even for in-document-derived `structural` data, not just externally-sourced data: a future smarter parser could revise it too, so there's no meaningfully more "permanent" subset of `structural` worth carving out — the `source` metadata key already lets a caller distinguish sub-origins later if that turns out to matter, without needing cascade eligibility to depend on it.

`human_annotated` entries are more nuanced — see "Human overrides," immediately below, for the split between what's protected and what cascades.

## Human overrides: a patch layer on top of the base graph, not a promotion tier

Chosen over an early draft that had human editing work by *promoting* an existing `structural`/`llm_extracted` entry in place, and over mutating overrides directly into the base layer — see [ADR-00029](../ADR/00029-human-overrides-patch-layer.md) for both rejected alternatives.

The settled model instead: `structural` and `llm_extracted` write an immutable base graph, never mutated or deleted by human action directly. `human_annotated` is a separate, small set of **override records**, each one of exactly two operation kinds:

- **`add`** — human-authored node/edge content, with an optional `overrides: [id, ...]` list of base-record ids it supersedes (empty/absent for a fresh addition; one-or-more when correcting or merging existing base entries — e.g. a human merging two duplicate LLM-extracted edges into one corrected edge is a single `add` with `overrides: [id_a, id_b]`, not a special "correct" case). `overrides`-having `add` entries are not cascade-eligible: an `add`'s content is exactly what a human intended it to be, independent of the machine record(s) it corrects a mistake in.
- **`reject`** — a pure veto, `targets: [id, ...]` (a list, not a single id — a human should be able to reject several instances of the same recurring false-positive pattern in one action rather than repeating the same judgment call per instance), no content payload of its own.

**Query resolution** falls out of this directly: for any base record, if a `reject` targets it, it's excluded from results; if an `add.overrides` targets it, the `add`'s content is returned in its place; if neither, the base record stands as-is unmodified. This is also why `structural`/`llm_extracted` remain sufficient as a standalone source of truth for the (expected-common) case where no human override exists at all — nothing about the override mechanism requires every entry to eventually get reviewed.

**Undo is trivial and needs no dedicated mechanism**: deleting an override record (`add` or `reject`) restores the base record's original effective state automatically, since the base was never touched in the first place. No promotion/demotion bookkeeping, no snapshot field, no reconciliation step.

**Cascade mechanics for overrides**, resolving cleanly now that overrides only ever reference base ids by list membership: when a base record is cascade-deleted, its id is pruned from every `add.overrides` and `reject.targets` list that contains it. A `reject` whose `targets` list becomes empty as a result is itself deleted (a veto with nothing left to veto is meaningless). An `add` whose `overrides` list becomes empty is *not* deleted — it simply becomes an ordinary standalone addition, which was always a valid state.

## Reference staleness on re-extraction: content-equality diffing for structural, full wipe-and-refresh for llm_extracted

Chosen over three rejected alternatives — fresh-id-per-pass (mirroring [Vector search](02-vector-search.md#chunk-identity-a-uuid-minted-per-parse-pass-not-derived-from-heading-text-or-position)'s `chunk_id` pattern), a content-hash-derived id, and fuzzy/similarity-based re-linking — see [ADR-00033](../ADR/00033-reference-staleness-content-equality-diffing.md) for why each fails, and why an override silently reattaching to the wrong entry is worse than one going stale.

Settled instead, split by layer since the drift-risk profiles genuinely differ:

- **`structural`** uses **entry-level content-equality diffing** — deterministic re-derivation carries little drift risk, so exact match is trustworthy. When a document's `structural` set is recomputed, each new entry is compared against the existing stored set for that document+type by exact content match (not id). An exact match keeps its existing id — untouched, no delete/reinsert — so any override referencing it keeps applying with zero staleness in the common case where nothing actually changed. A genuinely new entry gets a fresh id, inserted normally. An entry no longer present in the new pass is removed via the cascade mechanics above — except the affected override isn't silently pruned the way a document-deletion cascade prunes it; it's surfaced as needing review, mirroring the "derived, surfaced, not hidden" philosophy [Vector search already applies to `index_status`](02-vector-search.md#search-responses-always-carry-per-mechanism-index_status-including-fts) rather than assumed away. The exact surfacing shape is settled below, in "Surfacing orphaned overrides."
- **`llm_extracted`** re-extraction (e.g. a model upgrade) is never incremental or reconciled at the entry level — no matching is attempted at all. It's a deliberate, document-scoped **wipe-and-refresh**: every `llm_extracted` node/edge for that document is removed and replaced with a fresh extraction, all new ids, no exceptions. Trying to preserve ids across a model change would mean trusting a matcher precisely where the drift risk above makes it least trustworthy. Unlike a document-deletion cascade, though, the underlying document isn't gone — the concept a human overrode may well reappear under a new id in the fresh extraction — so overrides referencing the wiped scope aren't silently pruned by the ordinary override-cascade mechanics either: every affected override is flagged `needs_review` instead, preserving the human's prior judgement call for re-confirmation rather than discarding it.

This resolves the common case for free (`structural` re-parses over an unchanged document leave existing overrides untouched) while being honest, rather than clever, about the residual case where content genuinely changed — and, for `llm_extracted`, accepting a coarser but honest "review everything touched" over a finer-grained mechanism that can't be made safe against genuine model drift.

**What counts as "the same content" is now settled, for `structural` specifically** (this doesn't apply to `llm_extracted`, which never attempts matching at all). Comparison normalizes away purely *representational* differences before checking exact match: Unicode NFC (canonical composition — a precomposed `é` and `e`+combining-acute already mean the identical thing, so collapsing them to one form loses no information) and whitespace trim/collapse (leading, trailing, and internal runs). Both are safe specifically because nothing semantic is discarded — only a canonical encoding is chosen among several that already meant the same thing.

Case-folding, punctuation-stripping, and Unicode *compatibility* folding (NFKC) are deliberately excluded, even though they'd also close the `apple`→`Apple` gap — see [ADR-00033](../ADR/00033-reference-staleness-content-equality-diffing.md) for why. A re-parse that recases `apple` to `Apple` is therefore still treated as an unrelated removal-plus-addition under this design, and any override touching it still gets flagged `needs_review` — an accepted, conscious cost, not an oversight.

PDF-extraction artefacts like hyphenation across a line break (`trans-` / `formation`) are a related but distinct noise source, and are explicitly out of scope for this comparison: reconstructing word boundaries is the parser's job to get right consistently upstream, not something the diffing layer should guess at after the fact.

## Citation-graph data excluded from the structural layer, for now

Citation-graph data was extensively debated for inclusion in the structural layer — first as in-document reference-list parsing resolved to local `pointer:document` nodes, then as externally-sourced OpenAlex/CORE citation adjacency (ingress/egress edges, namespaced to each source's own Work/record identifiers) refreshed on a schedule. Both were considered and rejected, for related but distinct reasons — see [ADR-00034](../ADR/00034-citation-graph-data-excluded.md).

**Settled: the structural layer excludes citation-graph data entirely, for now** — neither in-document-derived nor externally-sourced. `structural`'s `source` metadata has exactly one live value, `"internal_parse"` (see "Provenance," above). This is a scoping decision, not an open question this document is trying to resolve — parked deliberately pending OpenAlex/CORE provider support landing, at which point whether and how to bring citation adjacency into the structural layer can be reconsidered with something actually able to make it worth its keep.

## Node scope: structural references stay document/note-scoped, concepts are cross-cutting

Two of this document's already-settled input layers turn out to split along a different axis than provenance: whether a node's identity is inherently tied to one document, or cuts across all of them. **Structural nodes** — chunks, headings, documents, and (extending the same reasoning to `NotesBackend`) notes — are unambiguously scoped to whichever document or note they come from; there's no sense in which a chunk "belongs" to more than one document. **Concept nodes**, by contrast, are cross-cutting by nature — the same concept (e.g. "transformer architecture") can and should be the same node whether it's mentioned in one paper or five, which is the entire point of "cross-paper concept linking" from this document's motivation. This holds regardless of whether a concept is `llm_extracted` or `human_annotated` — provenance type doesn't change whether a concept is shared, only who/how it was identified.

This resolves a real ambiguity left by content-equality diffing (settled above), which was designed comparing "the existing stored set for that document+type" — implicitly document-scoped identity, fine for structural nodes but in tension with concept nodes needing global identity. The resolution: diffing's document-scoping was only ever the right model for the structural layer; concepts sit outside it entirely, in their own top-level identity space.

## Node shape: pointer vs. owned content, without a separate "external reference" kind

Given the split above, structural nodes don't need to *own* any content — `VectorSearchBackend` already owns chunk content, `NotesBackend` already owns note content and anchors, and a document's content lives wherever `research_fetch` already put it. Duplicating any of that into a second, graph-owned copy would re-raise the same problem the override design already resolved once by rejecting `promoted_from`'s content-copying (see "Human overrides," above): don't copy data a node can instead point at. So a structural node is a **pointer**: `ref_type` (`"chunk"` | `"note"` | `"document"`) plus `ref_id`, the referenced backend's own id — two separate fields, not a single composite (see below for why not a namespaced id). `GraphSearchBackend` only stores the edges connecting these pointers to each other and to concept nodes; it never stores their content.

Concept nodes were originally motivated in part by the fetch ladder in [Discovery](../02-discovery.md): a citation to a work that isn't (yet) locally fetched has nothing for a pointer to reference, so it would need graph-owned content. That specific case is now deferred — see "Citation-graph data excluded from the structural layer, for now," above — so no `structural`-provenance concept node is created today. The general shape still stands, though, for `llm_extracted`/`human_annotated` concepts: one **owned-content** node shape, differentiated entirely by its existing `type`/`metadata` fields — chosen over a separate third node kind and over folding the pointer/owned-content discriminator into a namespaced `id`; see [ADR-00035](../ADR/00035-node-shape-pointer-vs-owned-content.md) for both rejected alternatives.

That leaves two disjoint field groups instead of three node kinds, and no explicit `kind`/discriminator field is needed at all: whether a node is a pointer or owned-content is fully recoverable from which fields are populated (`ref_type`+`ref_id` vs. `content`). `id` stays opaque; `ref_type` stays its own explicit, indexable column.

Settled node shape: `id` (opaque), `type` (provenance: `structural` | `llm_extracted` | `human_annotated`), `metadata` (open dict, per-type minimum, as already settled), `descriptors` (see below), plus exactly one of — `ref_type`+`ref_id` (pointer nodes: `chunk`/`note`/`document`), or `content` (owned/concept nodes: flat text, not a nested dict, since any structure it might need is already `metadata`'s job).

## Descriptors: qualifying content, kept separate from metadata

Nodes (and, more essentially, edges — see below) sometimes need to carry qualifiers on their content: `[apple, "red"]-[are, "generally", "except cox"]->[sweet]` is a real example, not a hypothetical — an edge can carry more than one independent qualifier, and both nodes and edges can carry them. These don't belong in `metadata`: `metadata`'s job, per its already-settled per-`type` minimum-required-key design, is describing *how an entry was produced* (`source`, `model`+`extraction_mode`, `annotator`) — provenance facts that vary by `type`. A descriptor like "red" is semantic content qualifying what the node *means*, orthogonal to provenance: a `human_annotated` "apple" and an `llm_extracted` "apple" could equally carry "red." Folding descriptors into `metadata` would mean anything reading them has to search an open, type-validated bag for a key with no schema guarantee — the same overloaded-field shape rejected twice already in this document.

Settled shape: `descriptors: [{"kind": str, "value": str}, ...]` — a list, since a single node/edge can carry more than one independent descriptor (as the `"are"` edge above does), and a list of dicts rather than tuples, since tuples have no native JSON/MCP-transport representation and would lose their self-description as plain 2-element arrays. `kind` stays an open string rather than a closed enum — "generally" (a frequency/confidence qualifier) and "except cox" (an exception/caveat) are visibly different kinds of descriptor, and there's no complete taxonomy yet to justify closing the set. `descriptors` defaults to an empty list — most nodes/edges won't carry any.

## Edge shape: same provenance triple as nodes, plus a relation_type that's content's counterpart

Every edge carries the same `id`/`type`/`metadata`/`descriptors` fields as a node — the provenance-plus-descriptor combination was never node-specific, per the original "every node/edge carries..." provenance rule. What's edge-specific is `relation_type`: the semantic label of what the edge *is* (`"cites"`, `"mentions"`, `"is_a"`, `"are"`), directly analogous to a node's `content` — both are flat, open-vocabulary text naming what the thing means, not structured provenance. Unlike `content`, though, `relation_type` isn't conditional on a pointer/owned split — edges don't have that split at all, so every edge carries one unconditionally. Like `content`, `descriptors.kind`, and `metadata`'s open extension, `relation_type` stays an open string rather than a closed enum: there's no complete relation-type taxonomy to justify closing it, and each of this document's three input layers is likely to need its own vocabulary (structural: `"cites"`, `"contains"`, `"mentions"`; LLM/human: whatever the extracted or annotated relation actually is).

Two more fields carry the edge's endpoints: `source_id` and `target_id`, both referencing node ids — pointer or concept, a single homogeneous id space, since node `id` stays opaque regardless of kind. Edges are directed: `[apple]-[are]->[sweet]` is `source_id` = apple's node id, `relation_type` = `"are"`, `target_id` = sweet's node id.

**Cascade on endpoint deletion.** When either `source_id` or `target_id`'s node is deleted, the edge is cascade-deleted too — unconditionally, regardless of the edge's own provenance type, since an edge with a missing endpoint can never be valid. This is a genuinely new cascade rule, distinct from `structural`/`llm_extracted` cascade-eligibility (which is about a node/edge's *own* provenance): even a `human_annotated` edge, normally protected from cascade, is deleted if one of its endpoints is deleted — an edge can't outlive what it connects. Any override referencing the cascade-deleted edge follows the override-cascade mechanics already settled: pruned from `add.overrides`/`reject.targets` lists, with a `reject` whose `targets` empties being deleted, and an `add` whose `overrides` empties surviving as a standalone addition.

**Addendum: `weight: float | None = None`.** Surfaced by designing `GraphAlgorithmsBackend`'s per-algorithm signatures (below): `dijkstra`, `minimum_spanning_tree`, and `pagerank`'s optional weighting all need a numeric edge attribute the shape below didn't originally have a place for. It doesn't belong in `metadata` (provenance-only, per its own already-settled job) or `descriptors` (`value` is typed `str`, and descriptors qualify what an edge *means*, not a numeric algorithm input) — a dedicated field is the honest fix, additive to the shape rather than a restructuring of it. `weight` carries no specific semantic meaning of its own yet — no input layer currently derives a value for it — but is left open for any layer to set later (structural from citation frequency, LLM extraction from confidence, human manually), `null` meaning unweighted wherever an algorithm needs a value and none was supplied.

Settled edge shape: `id` (opaque), `type` (provenance), `metadata` (open dict, per-type minimum), `descriptors` (`list[{"kind": str, "value": str}]`, open kind, may be empty), `relation_type` (open string), `source_id`+`target_id` (endpoint node ids, directed), `weight` (`float | None`, default `null`).

## Read/traversal interface: `get_nodes`, `get_edges`, `neighbors`

`get_nodes`/`get_edges` are **batch-only** — with a single-id input list, they still act as single-read methods, so there's no separate singular form to keep in sync. Signatures:

- `get_nodes(ids: list[str]) -> {"nodes": [Node, ...], "not_found": [str, ...]}`
- `get_edges(ids: list[str]) -> {"edges": [Edge, ...], "not_found": [str, ...]}`

`not_found` is computed as the set difference between requested and returned ids, the exact pattern [`research_arxiv_fetch_metadata`](../06-interface-specification.md#research_arxiv_fetch_metadata) already uses — misses are reported alongside the hits, not raised as an error, since a batch call partially succeeding is the expected common case, not a failure. `not_found` covers both a genuinely nonexistent id and one excluded by a `reject`: from the caller's perspective, a rejected record is indistinguishable from one that was never there — both are absent from the override-resolved graph query resolution already defines.

**Override resolution is transparent by construction, no `override_id` field needed.** When a requested id is a base record targeted by an `add.overrides`, the SQL view resolving `get_nodes`/`get_edges` (per "Graph algorithms," above) keeps the *requested* id as the returned record's `id` — but every other field (`type`, `metadata`, `descriptors`, `content`/`relation_type`) comes from the overriding `add`. A caller who looked up a `structural`/`llm_extracted` id and gets back `type: "human_annotated"` already has the override signal for free, without a dedicated flag — the same "recoverable from existing fields, no discriminator" pattern this document already applies to the node pointer/owned-content split. An `add` with a non-empty `overrides` list is a patch, not a standalone node: it's reachable only via the base id(s) it overrides, not independently by its own id. An `add` with an empty/absent `overrides` list is an ordinary node/edge, reachable by its own id like any other.

`neighbors` is single-id, not batch — there's no partial-success case to report field-wise, so a nonexistent `node_id` fails outright with a `not_found` error (the same name already used as a field elsewhere in this document, raised here as an error instead since there's no batch to attach it to) rather than being silently omitted. Signature:

- `neighbors(node_id: str, direction: "out" | "in" | "both" = "both", relation_type: list[str] | None = None, hop_limit: int = 1) -> list[{"node_id": str, "hop": int, "edge_id": str}]`

`relation_type` is `list[str] | None` (any-of match when given, `None` meaning any relation type), matching `research_graph_status`'s own `type: list[str]` filter convention below rather than introducing a singular-string filter shape elsewhere in this document. `hop_limit` defaults to `1` (direct neighbors only) and is hard-capped at `4` — deliberately conservative, since this is a live, override-resolved BFS run per call, not a precomputed index, and "neighbours" stops meaning much past a handful of hops. `hop_limit > 4` fails with `invalid_request` rather than being silently clamped, consistent with this document's general aversion to anything that changes caller-requested behaviour without saying so. This cap has no bearing on `GraphAlgorithmsBackend`: algorithms pull the whole override-resolved node/edge set in one bulk export to build their `networkx.Graph` (per "Graph algorithms," above) — they share `neighbors`' underlying live-resolution mechanism, but never call `neighbors` itself or inherit its hop cap. A caller wanting to explore past 4 hops can chain calls, anchoring a fresh `neighbors` call on a node returned at the previous call's hop limit — an uncommon usage shape, not one worth widening the cap to avoid.

The cap isn't an arbitrary round number, either: the two scenarios that would genuinely need to go deeper are already served elsewhere in the settled catalogue without any hop limit at all — long-range connectivity between two specific concepts is `dijkstra`'s job (a targeted point-to-point search, not a broadcast outward from one node), and tracing an idea's provenance arbitrarily far back is `ancestors`/`descendants`'s job (full transitive closure over a DAG, unbounded by design). `neighbors`' own job — what's immediately around this node — doesn't need to go past a handful of hops, because anything that genuinely does is a different question with its own purpose-built tool. Following the same "hard caps, not defaults, are configurable" split settled for `betweenness_centrality`'s `k` (below): the hard cap (`4`) is exposed as `PRIORIS_MCP_GRAPH_NEIGHBORS_HOP_LIMIT_MAX` — an empirically-comfortable ceiling for this project's own usage patterns, not a universal constant — while the per-call default (`1`) stays a fixed code constant, since a caller can already ask for more per call up to whatever ceiling is configured.

Each entry in the result is per `(node_id, hop, edge_id)`, not deduplicated to one edge per node: if more than one edge reaches the same node at the same hop distance, every such edge gets its own entry. Concretely, this is a level-by-level BFS where a node is only marked visited (ineligible for discovery at a *later* hop) once its entire current-hop frontier has finished being processed — so two edges landing on the same node at the same hop both get recorded, while a third edge reaching that node one hop later doesn't. This matches this document's general "surfaced, not hidden" bias (the same instinct behind `needs_review` and `index_status`) over silently picking one edge and discarding the rest.

## Write primitives: `add_node`/`add_edge` (generic), `reject` (new), `edit_node`/`edit_edge`/`edit_reject` (human-only)

`add_node`/`add_edge` are genuinely shared across all three input layers named above — structural code calls them directly (`type="structural"`), the LLM-extraction convenience wrapper calls them internally (`type="llm_extracted"`), and the human layer's own CRUD surface calls them with `type="human_annotated"` fixed by that thinner wrapper rather than exposed as a caller-settable argument. `type` stays a parameter on these two specifically *because* they're shared:

```python
add_node(
    type: Literal["structural", "llm_extracted", "human_annotated"],
    metadata: dict,
    descriptors: list[Descriptor] = [],
    ref_type: Literal["chunk", "note", "document"] | None = None,
    ref_id: str | None = None,
    content: str | None = None,
    overrides: list[str] | None = None,   # only meaningful when type == "human_annotated"
) -> Node   # id is server-assigned, never caller-supplied
```
Exactly one of (`ref_type`+`ref_id`) or `content` must be given, failing `invalid_request` otherwise — the same "fully-empty fails validation" pattern `Anchor` already uses in `NotesBackend`. `metadata` is validated against its already-settled per-`type` minimum. `overrides` supplied when `type != "human_annotated"` fails `invalid_request`, since only the override mechanism uses it.

```python
add_edge(
    type: Literal["structural", "llm_extracted", "human_annotated"],
    metadata: dict,
    relation_type: str,
    source_id: str,
    target_id: str,
    descriptors: list[Descriptor] = [],
    weight: float | None = None,
    overrides: list[str] | None = None,
) -> Edge
```
`source_id`/`target_id` not resolving to existing nodes fails `not_found`.

**`reject` doesn't fit either shape and needs its own primitive.** A reject record has no content, no `ref_type`/`relation_type` — just a veto over a list of ids that can mix node and edge ids in one action (e.g. rejecting an extracted concept *and* the edges asserting it, together). It's always `type="human_annotated"`, so unlike `add_node`/`add_edge`, `reject` doesn't take `type` at all:
```python
reject(targets: list[str], metadata: dict) -> RejectRecord   # {"id", "type": "human_annotated", "targets", "metadata", "needs_review"}
```
One unified `reject`, not split by node/edge target — there's no shape difference between vetoing a node-id and vetoing an edge-id, since a reject carries no content either way.

**`edit_node`/`edit_edge`/`edit_reject` exist because delete-then-recreate isn't a safe substitute for correcting a human's own entry.** Cascade on endpoint deletion (above) deletes every edge touching a deleted node unconditionally, regardless of the edge's own provenance type — so deleting a human's own `add` node to fix a typo would collaterally destroy every edge attached to it, and any `overrides`/`targets` list referencing it would get pruned by the ordinary override-cascade mechanics. In-place edit avoids all of that, since the id never changes. Also `type`-less, for the same reason `reject` is:
```python
edit_node(id: str, metadata: dict | None = None, descriptors: list[Descriptor] | None = None,
           content: str | None = None, overrides: list[str] | None = None) -> Node
edit_edge(id: str, metadata: dict | None = None, descriptors: list[Descriptor] | None = None,
           relation_type: str | None = None, weight: float | None = None, overrides: list[str] | None = None) -> Edge
edit_reject(id: str, targets: list[str]) -> RejectRecord
```
Patch semantics throughout — only supplied fields change, unset ones keep their current value. **`edit_reject` replaces the target `RejectRecord`'s `targets` list wholesale** (add or drop which ids it vetoes); it does not "reject an edit," and it never touches any `add`/base record — naming this explicitly since the symmetry with `edit_node`/`edit_edge` could otherwise suggest it edits some other record's content.

Legal only on `type == "human_annotated"` records, following directly from the already-settled immutable-base-graph rule — attempting to edit a `structural`/`llm_extracted` record fails `invalid_request`; a nonexistent `id` fails `not_found`. Deliberately excluded from what `edit_node`/`edit_edge` can change: `ref_type`/`ref_id`/`source_id`/`target_id` — repointing what a node references or what an edge connects is a different node/edge, not a content correction, and should go through delete-and-recreate, where cascade-on-endpoint-change is the *correct* behaviour rather than something to route around.

**MCP tool wiring: one tool per primitive, not consolidated.** Mirrors `NotesBackend`'s own already-shipped precedent (`research_notes_create`/`research_notes_read`/... as separate tools, not one tool with an operation-kind parameter) and this document's own repeated refusal to consolidate across the node/edge axis anywhere else (`get_nodes`/`get_edges`, `add_node`/`add_edge`, `edit_node`/`edit_edge` are never merged). Six tools, thin wrappers fixing `type="human_annotated"` where relevant: `research_graph_add_node`, `research_graph_add_edge`, `research_graph_reject`, `research_graph_edit_node`, `research_graph_edit_edge`, `research_graph_edit_reject` — matching the `research_<domain>_<verb>` naming every existing tool already uses. That prefix isn't an arbitrary product-wide label: it corresponds specifically to `ResearchPublicationProvider`, the only provider grouping that exists today (see [Architecture → Provider groupings](../01-architecture.md#provider-groupings)) — a future `PatentProvider` grouping would naturally get its own `patent_<domain>_<verb>` prefix, not a `research_`-prefixed patents tool, consistent with graph/notes/vector data never being expected to mix across groupings either (see "Provider-grouping isolation," above). `annotator` (required `human_annotated` metadata) is exposed as its own top-level parameter on these tools rather than nested inside `metadata`, mirroring `research_notes_create`'s `author_name` (`null` meaning self).

## `GraphExtractionBackend.extract(text)`

```python
async def extract(text: str) -> tuple[list[ExtractedNode], list[ExtractedEdge]]
```
- `ExtractedNode = {"content": str, "descriptors": list[Descriptor] = [], "metadata": dict = {}}`
- `ExtractedEdge = {"source_index": int, "target_index": int, "relation_type": str, "descriptors": list[Descriptor] = [], "metadata": dict = {}}`

Neither carries an `id` — `source_index`/`target_index` are 0-based positions into the returned node list, since extracted nodes have no real id until `GraphSearchBackend.index_entries` calls `add_node` per entry and substitutes the resolved ids into the edges it then passes to `add_edge`. `metadata` here is *per-item*, distinct from the uniform run-level `model`/`extraction_mode`/`version` `index_entries` already knows from which `GraphExtractionBackend` implementation it injected — it's an escape valve for whatever per-item signal a specific implementation naturally produces (confidence, evidence span, reasoning excerpt), merged with the uniform run-level keys by `index_entries` rather than requiring every implementation to repeat them per item. `async`, matching `EmbeddingBackend.embed`'s own settled `async` ([Vector search](02-vector-search.md#embeddingbackend-is-a-pluggable-interface-injected-into-vectorsearchbackend)) for the same reason: a real LLM API call has real network latency.

**Deliberately doesn't attempt cross-mention entity resolution.** Recognising that "transformer architecture" mentioned in one paper is the same concept as one already extracted from another is exactly the same false-merge risk already used to reject fuzzy re-linking for reference staleness (above) — arguably worse here, since concept matching is fuzzier than content-equality. Every mention creates its own concept node; cross-mention merging is deferred to human review via the already-designed `add.overrides` mechanism, which already anticipates exactly this shape ("a human merging two duplicate LLM-extracted edges into one corrected edge is a single `add` with `overrides: [id_a, id_b]`"). This keeps `extract` a pure function of `text` alone, no dependency on existing graph state — mirroring `embed(text)`'s equally self-contained shape.

## Surfacing orphaned overrides: a persistent `needs_review` flag, plus a dedicated status tool

A response field on every graph-touching call was considered and rejected: most reads (query resolution, a plain node/edge fetch) have nothing to do with re-extraction, so bolting an orphan-review field onto all of them for the rare case would bloat their semantics for no benefit to the common caller — the same reasoning [Discovery](../02-discovery.md#surfacing-shape-a-new-tool-research_discovery-not-a-mode-on-research_search_fetched) already applied when it gave discovery its own tool rather than folding it into `research_search_fetched`'s `mode` enum.

Instead, orphan-review state is split into two tiers, mirroring how `index_status` isn't just returned once but tracked as durable per-document/note state ([Vector search](02-vector-search.md#search-responses-always-carry-per-mechanism-index_status-including-fts)):

- **Persistent flag.** Every override record (`add`/`reject`) gains a `needs_review: bool` field, defaulting `false`. Content-equality diffing sets it `true`, instead of hard-cascading the override, when a re-parse or refresh-triggered re-sync removes one of its targets — the existing behaviour described in "Reference staleness on re-extraction," above, now with a concrete field to carry that state.
- **In-the-moment notification.** The re-parse/re-sync tool's own response additionally carries the immediate delta for that call (`overrides_flagged_needs_review: [id, ...]`) — a convenience for a caller watching that specific call, layered on top of the persistent flag, not a replacement for it. A caller who isn't watching that call can still discover flagged overrides later, since the flag itself is durable.

**New tool: `research_graph_status`.** A dedicated status/observability surface for `GraphSearchBackend`, the graph's counterpart to `index_status` — but as its own tool rather than folded into search responses, since graph status isn't produced by a search call the way `index_status` rides along with `fts`/`vector`/`graph` results. Signature: `research_graph_status(document_ids: list[str] = [], note_ids: list[str] = [], type: list[str] = [], needs_review: bool | None = None)`; no filters given returns whole-graph totals. Response, per matching layer/scope: node count, edge count, a last-updated timestamp, and a flat list of `needs_review`-flagged node/edge ids.

**Filters considered and dropped.** `node_ids`/`edge_ids` were considered and rejected: this is a status-check tool, not a graph-read one — resolving individual node/edge detail by id is `get_nodes`/`get_edges`'s job (see "Read/traversal interface," above). It would also be of limited use regardless, since ids for *changed* content don't survive the exact re-parse/re-sync event this tool exists to check on (only unchanged content keeps its id, per content-equality diffing) — a caller can't reliably hold onto a node/edge id across the event it's trying to inspect. `document_ids`/`note_ids` don't have that problem, since document/note identity is exactly what content-equality diffing preserves across re-runs. `source` (structural sub-origin, e.g. `openalex` vs. `internal_parse`) was also considered and dropped as not relevant to a status check specifically.

The flagged-items list intentionally carries ids only, not full override/node/edge detail — a caller wanting the full record already has a graph-read tool for that; duplicating that detail here would mean this tool and that read tool disagree about which one owns "what does this record actually contain."
